# Command-first, не terminal-first

Сначала определяется прикладная операция: намерение, входы/defaults, результат,
существенные отказы, эффекты и допустимый повтор. CLI разбирает аргументы и
представляет результат. Будущие GUI/MCP смогут обращаться к тому же владельцу,
но не обязаны запускать CLI-процесс и не получают свою копию правил.

До рефакторинга `cli.py` совмещает Typer с разрешением конфигурации, выбором
command services, retries/timeout, сборкой envelope и admission для live doctor.
При этом `commands/`, `core/`, `batch/`, `doctor/` и runner уже дают полезные
переиспользуемые границы. Цель — выделить недостающую прикладную оркестрацию,
а не переписать проверенные механизмы. Конкретные сигнатуры, файлы и срезы
определяются [планом command-first-рефакторинга](../plans/command-first-refactor.md)
до изменения кода; план не описывает уже реализованный API.

## Один владелец ответственности

- Прикладной API координирует конфигурацию, операции, defaults, admission и результаты.
- Предметные инварианты остаются у существующих policy/path/command owners; адаптер
  не может обойти их альтернативным путём.
- rclone runner исполняет literal argv, ограничивает процессы и переводит ошибки;
  оболочка не собирает shell-команду из пользовательского ввода.
- Journal — владелец приватной записи публичных ссылок; диагностические события
  не заменяют его и не становятся источником состояния.
- CLI владеет парсером, help, форматированием и process exit. Прикладная операция
  не печатает, не вызывает Typer exit и не требует импортировать GUI/CLI/MCP SDK.

Общие данные не означают общую живую сессию. Нынешние синхронные операции не
требуют очереди, Job Manager, IPC, command bus, CQRS или Event Sourcing. Если
появится требование работы после завершения процесса или общего изменяемого
workspace, владелец и lifecycle проектируются явно. Профили A–D из методики —
варианты гарантий, а не ступени обязательной зрелости.

## Совместимость и сохранность

Действующий [CLI-контракт](../02-command-contract.md) и JSON-схемы сохраняются:
имена/флаги, precedence config/env/аргументов, envelope/exit codes, batch partial
failure, zero-backend dry-run, отсутствие скрытого setup, запрет write retries,
подтверждения, public root, dangerous-file, redaction и private journal.
Прямой API обязан обеспечивать те же применимые защиты, не только CLI.

После внешнего write и потери ответа нельзя считать, что эффекта не было.
Не вводим автоматический повтор записи или обещание exactly-once. Частичный
исход публикации/пакета остаётся явным; cleanup ограничивается своими ресурсами.
Рефакторинг не мигрирует пользовательские настройки и journal без необходимости.

## Контракт и проверка

Каждый публичный API фиксирует входы/defaults, результат/ошибку, эффект, порядок
валидации и применимые retries/confirmation. Один канон лучше параллельных схем.
Runtime-валидация не является аутентификацией или новым правом доступа.
Для будущего удалённого MCP отдельно потребуется доверенный контекст принимающей
стороны; значение `yes` не является доказательством внешней авторизации.

Проверяем настоящий прикладной путь напрямую и через CLI, существенный отказ,
сохранность, сериализованный вывод и отсутствие зависимости ядра от оболочки.
Структурный import-test полезен, но без runtime-сценария недостаточен.
Неизменённые платформенные механизмы не переписываются ради новой диаграммы.
