# Назначение и приоритеты

Hermes MailCloud даёт агенту и человеку предсказуемые операции над Mail.ru Cloud:
чтение метаданных, перенос файлов, управление каталогами и ограниченную публикацию.
Существующая поставка — Python CLI версии 0.1.0, внешний rclone и JSON-контракт.
Направление развития — command-first: операция принадлежит приложению, способ
вызова является сменным адаптером. Этот документ задаёт причины и приоритеты,
а не утверждает, что новый API уже реализован.

При конфликте требований приоритеты таковы:

1. Сохранность пользовательских данных, credentials и приватных capability-ссылок.
2. Верность результата и совместимость действующего машинного контракта.
3. Понятная ответственность, воспроизводимая диагностика и проверка реального пути.
4. Простота сопровождения и возможность добавлять оболочки без копирования правил.
5. Удобство и скорость в пределах первых четырёх пунктов.

GUI, MCP, собственный Mail.ru API-клиент, демон, фоновые задачи и синхронизация
не входят в текущий рефакторинг. Будущая оболочка не оправдывает создание всего
этого заранее. Работающий CLI сохраняется.

## Инженерные основания

**Работающий результат важнее количества кода и отчётов.** План нужен для
исполнения и проверки; наличие каталога application само по себе ничего не
доказывает. Отказ опасной операции — такой же обязательный результат, как успех.

**Простота и предсказуемость важнее демонстрации паттернов.** Используем существующие
policy, command services, runner, journal и envelope. Новая абстракция должна
устранять реальное смешение ответственности, а не переименовывать его.

**Проверка соразмерна риску.** Изменение общей границы требует прямого вызова
прикладного API, соединённого CLI-пути и проверки сохранённых защит. Обычные тесты
синтетические и автономные; живые проверки требуют отдельной применимой власти.

**Знание имеет владельца и границу доказательства.** Требование, найденная
реализация, гипотеза и выполненный тест различаются. Принятый план не является
реализованной функцией; дата Markdown не подтверждает поведение приложения.

**Документация уменьшает цену следующего изменения.** Правило имеет один канон.
Нужные архитектура, контракт и ограничения обновляются вместе с изменением;
не затронутые документы не получают искусственную новую дату.

**Завершение конечно.** До реализации задаются критерии; после достаточной
проверки и независимой приёмки срез заканчивается. Разрешение на разработку
не означает разрешение на commit, push, release или действия с рабочим облаком.

## Применение и пересмотр

Oracle планирует архитектурную дельту; кодер реализует и проверяет; независимый
проверяющий принимает; Hermes координирует. Порядок — в
[рабочем цикле](../agent-workflow.md). Пересмотр философии нужен при изменении
назначения, аудитории, данных или реальных ограничений, не после каждого теста.

Основание адаптации: [Project Foundation Kit 0.3.0](../../tools/project-foundation/README.md),
включая его LICENSE и происхождение. Содержимое импортированного пакета —
методическая зависимость, проектные решения принадлежат этому репозиторию.
