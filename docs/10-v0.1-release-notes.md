# 0.1.0 Release Notes — Hermes MailCloud

**0.1.0 is the stable GitHub release**, tag `v0.1.0`, not a PyPI publication.
It promotes the accepted 0.1 functionality with synchronized package metadata
and clearer installation/connection documentation; it adds no new runtime features.
Stable status is not evidence of untested compatibility or universal production
readiness. Historical `v0.1.0a0` and `v0.1.0a1` refs/releases remain unchanged.

## Functionality carried forward from the alpha series

- Native Windows private-journal ACL/locking and bounded rclone process-tree
  supervision, alongside the separate POSIX backends. Readers reopen and fully
  revalidate retired Windows journal generations within a bounded retry policy;
  zero-link handles and unsafe replacements are not accepted.
- Explicit per-user `setup` for pinned official rclone; no bundled executable,
  implicit bootstrap, global installation or cloud-account configuration.
- Directory `stat` accepts the native empty root metadata only for a genuine
  directory, retaining malformed-file/listing guards.
- Portable installed-wheel smoke and Windows/Linux × Python 3.12/3.13 CI.
  Runner-local cache selection happens after runner assignment, not in a
  pre-run job environment expression.

## Compatibility and installation

For regular agent use, the recommended isolated persistent installation is
`uv tool install --python 3.12 https://github.com/VladimirMonin/hermes-mailcloud/releases/download/v0.1.0/hermes_mailcloud-0.1.0-py3-none-any.whl`.
`uv tool` is built into uv, convenient but not mandatory; source checkout/`uv run`
is a separate development route. See the guide for installing uv, PATH discovery,
non-uv-tool alternatives and explicitly replacing an older GitHub-wheel install.

Python >=3.12 is declared; Python 3.12 and 3.13 are the qualification targets. Native Windows journal/setup
storage requires the documented local fixed NTFS/private-path boundary. Windows
local evidence used elevated processes; genuine ordinary-user Windows remains
unqualified. That is not evidence of an Administrator prerequisite. CI coverage
is not ordinary-logon or complete platform qualification.

Release deliverables are a wheel, source distribution and `SHA256SUMS`; rclone,
credentials and internal evidence are not bundled. See
[installation](11-local-installation.md#install-from-a-release-wheel).
Public-link HTTP success may be an HTML landing page, not document-byte download.
The unsupported features below remain unsupported.

### Retained installed-agent/cloud boundary

Prior installed-alpha checks used a per-user uv tool and official rclone from a
Windows agent outside the checkout, native argument arrays, JSON and exit statuses.
Explicit matching HMC config/profile plus process RCLONE_CONFIG selected an existing
connection without reading/copying credentials. Real owned-directory creation,
upload/list/stat/download with byte+SHA comparison, rename and own cleanup passed.
An earlier default-connection refusal did not establish missing credentials. These
are historical scoped alpha observations, **not fresh 0.1.0 cloud checks**. Windows
checks were elevated: ordinary-user runtime remains unqualified, proving neither
an Administrator requirement nor ordinary-user support.

## Release surface

This document records the frozen v0.1 package surface. The package is an
rclone-backed, JSON-first CLI; it does not bundle rclone, a Mail.ru client, or
credentials.

Implemented commands:

- `version`
- `setup` — explicit user-scoped rclone preparation, not cloud configuration
- `doctor`
- `ls`, `stat`
- `mkdir`, `upload`, `download`, `mv`, `cp`, `rm`
- `publish`, `link`
- `batch`

`doctor --json` is read-only. `doctor --json --live --yes` is an explicitly
mutating diagnostic: it generates its own unique `/TEST/hermes-mailcloud-*`
roots, records redacted capability evidence, and stops rather than widening
cleanup if same-run cleanup cannot be proved.

## Safety contract

- `rm` and `publish` require `--yes` for real execution; a write-bearing
  `batch` requires outer `--yes`; `doctor --live` requires `--yes`.
- `publish` and `link` are limited to `/Hermes/public`, reject dangerous file
  names, and require an owner-private `links_journal` before backend side
  effects.
- Dry-run validates before backend use and never writes a journal, creates a
  public link, or mutates cloud state.
- Public URLs and raw provider diagnostics remain owner-private; normal JSON,
  documentation, CI output, Git, and agent handoffs contain only redacted data
  or fingerprints.
- No v0.1 operation automatically retries a write after an ambiguous result.

## Explicit non-features

`unlink` is not shipped unless a bounded live probe proves both `rclone link
--unlink` and public-URL invalidation. There is no v0.1 private-API fallback.
The following are also outside v0.1: sync, direct-download resolution, public
link expiry or passwords, full link audit, and an auth command.

## Build and installation gate

The release package is built with `uv build`. The required portable package smoke
installs the built wheel with locked runtime-only dependencies in a fresh runtime
outside the checkout. It checks import provenance, the real console launcher
(`--help`, version and read-only JSON doctor), and fake-backed installed
file/public/batch/journal scenarios. It does not require an rclone configuration,
credentials, or a live cloud operation. See the
[package smoke procedure](../README.md#package-smoke-test).

`.github/workflows/ci.yml` defines Windows/Linux × Python 3.12/3.13 runtime
cells with disjoint `pytest -m "not live"` packs, wheel/sdist build and clean
installed smoke. A separate job checks the lockfile, Ruff lint and formatting.
The workflow intentionally has no Mail.ru credential inputs and never runs
probe scripts or live tests.

## Live release gate

A release decision still requires a bounded final live canary using only
freshly generated objects under one or more `/TEST/<unique-run-id>/`
descendants. The canary must establish an absent target before mutation, keep
existing objects outside `/TEST` metadata/list-only, and prove same-run cleanup
by read-back. Capability data and raw provider output remain private evidence,
not release-document content.
