# v0.1 Release Notes — Hermes MailCloud

## Current candidate and future publication boundary

The current working tree is a private, unpublished `0.1.0a0` candidate. It is
not a public source release, tagged release, GitHub Release, or PyPI
distribution. The following identity is a future release policy, not a claim
that any publication surface already exists.

After owner-approved public visibility, an accepted release commit, and the
required external release gates, the release identity will be:

| Identity | Value |
|---|---|
| Distribution / runtime package | `hermes-mailcloud` / `hermes_mailcloud` |
| Version | `0.1.0a0` (alpha) |
| Release tag | an annotated, never-moved `v0.1.0a0` tag |
| Source | the public GitHub repository `VladimirMonin/hermes-mailcloud` at that tag or its resolved commit |
| GitHub Release | one release from that exact tag after the offline gates pass |
| PyPI | one immutable `hermes-mailcloud==0.1.0a0` upload built from that same tag/commit |

The source repository, GitHub Release, and PyPI are distinct publication
surfaces. A source checkout is not a GitHub Release; a GitHub Release is not a
PyPI upload; local `dist/` files are not release artifacts until this policy's
identity and verification gates bind them to the accepted tag and commit.

Never retag, replace, delete-and-reuse, or overwrite a released artifact. If a
release-relevant file changes after the release commit is frozen or tag is
created, use `0.1.0a1` consistently in package metadata, runtime, tag, release,
documentation, artifacts, and PyPI upload. The release workflow does not use
`skip-existing`.

Before a PyPI upload, the owner must verify all of the following external
prerequisites: public visibility is approved, the immutable tag exists, the
GitHub `pypi` environment exists with its required reviewer, and PyPI Trusted
Publishing is configured for this exact tuple:

```text
hermes-mailcloud / VladimirMonin / hermes-mailcloud / publish.yml / pypi
```

The currently missing protected `pypi` environment is an external prerequisite,
not a repository-byte defect and not something this document or workflow can
create. The ordinary CI workflow is offline and read-only (`contents: read`).
The candidate publish workflow is designed to receive `id-token: write` only in
the protected publish job after that environment gate is verified. No
`PYPI_TOKEN` is used or accepted by this workflow.

## Release surface

This document records the frozen v0.1 package surface. The package is an
rclone-backed, JSON-first CLI; it does not bundle rclone, a Mail.ru client, or
credentials.

Implemented commands:

- `version`
- `doctor`
- `ls`, `stat`
- `mkdir`, `upload`, `download`, `mv`, `cp`, `rm`
- `publish`, `link`
- `batch`

`doctor --json` is read-only. `doctor --json --live --yes` is an explicitly
mutating diagnostic: it generates its own unique `/TEST/hermes-mailcloud-*`
roots, records redacted capability evidence, and stops rather than widening
cleanup if same-run cleanup cannot be proved.

## Safety contract

- `rm` and `publish` require `--yes` for real execution; a write-bearing
  `batch` requires outer `--yes`; `doctor --live` requires `--yes`.
- `publish` and `link` are limited to `/Hermes/public`, reject dangerous file
  names, and require an owner-private `links_journal` before backend side
  effects.
- Dry-run validates before backend use and never writes a journal, creates a
  public link, or mutates cloud state.
- Public URLs and raw provider diagnostics remain owner-private; normal JSON,
  documentation, CI output, Git, and agent handoffs contain only redacted data
  or fingerprints.
- No v0.1 operation automatically retries a write after an ambiguous result.

## Explicit non-features

`unlink` is not shipped unless a bounded live probe proves both `rclone link
--unlink` and public-URL invalidation. There is no v0.1 private-API fallback.
The following are also outside v0.1: sync, direct-download resolution, public
link expiry or passwords, full link audit, and an auth command.

## Deterministic build, artifact, and runtime gates

After the immutable tag exists, build both artifacts once with `uv build` from
that exact tagged commit. The future release candidate is accepted only when all
of these deterministic gates pass:

1. `uv lock --check`, Ruff, formatting, and `pytest -m "not live"` pass.
2. The runtime version, package metadata, `License-Expression: MIT`, project
   URLs, and declared license files are exactly the release identity above.
3. The wheel and source archive each carry `LICENSE` and
   `THIRD_PARTY_NOTICES.md`; archive payloads and metadata are inspected rather
   than inferred from the checkout.
4. Separate clean Python 3.12 environments install both the candidate wheel and
   source archive under runtime constraints generated from the committed lock:

   ```bash
   uv export --locked --no-dev --no-emit-project --no-hashes
   ```

   After normalized project names and platform markers are evaluated, the full
   installed runtime map must equal both that export map and the machine-readable
   ledger in `THIRD_PARTY_NOTICES.md`. This prevents a broadly resolved tool
   environment from standing in for the locked release graph.
5. The installed command passes `--help`, `--json version`, and read-only
   `--json doctor` without credentials or a live cloud operation.

`.github/workflows/ci.yml` is the offline authority for those gates. It has no
Mail.ru credentials, never runs probe scripts or live tests, and has only
`contents: read`. After the external prerequisites are verified,
`.github/workflows/publish.yml` must require a successful `ci.yml` run for the
exact release commit, validate the annotated tag/version/commit and artifact
identity, pass the one build output to its protected publish job, and upload it
through Trusted Publishing.

## Live release gate

A release decision still requires a bounded final live canary using only
freshly generated objects under one or more `/TEST/<unique-run-id>/`
descendants. The canary must establish an absent target before mutation, keep
existing objects outside `/TEST` metadata/list-only, and prove same-run cleanup
by read-back. Capability data and raw provider output remain private evidence,
not release-document content.

## License and provenance

The distribution is MIT-licensed under `LICENSE`. `THIRD_PARTY_NOTICES.md`
