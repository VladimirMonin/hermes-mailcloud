# ADR 0003. Do not copy GPL code

> Статус: accepted  
> Дата: 2026-07-04  
> Проект: `hermes-mailcloud`


## Контекст

При исследовании Mail.ru Cloud найдены исторические reverse-engineered клиенты. Часть из них распространяется под permissive-лицензиями, часть — под GPL.

Особенно важный случай: `mad-gooze/PyMailCloud` распространяется под GPL-2.0.

Этот проект полезен как исторический reference по endpoint-ам `file/publish` и `file/unpublish`, но копирование его кода может повлиять на лицензионную модель `hermes-mailcloud`.

## Решение

Не копировать GPL-код в проект.

`PyMailCloud` использовать только как research reference.

Разрешено:

- читать README и код для понимания исторического поведения API;
- фиксировать endpoint-и в research summary;
- писать clean-room реализацию с нуля;
- ссылаться на проект в `THIRD_PARTY_NOTICES.md`.

Запрещено:

- копировать функции;
- копировать классы;
- копировать структуру реализации;
- vendor-ить GPL-пакет;
- адаптировать код с минимальными изменениями.

## Обоснование

Проект планируется под MIT. Для этого нужно избегать включения GPL-кода в распространяемый код проекта.

Также в v0.1 вообще не нужен прямой private API implementation, потому что основной backend — `rclone` subprocess.

## Последствия

Плюсы:

- чистая лицензия проекта;
- меньше юридических рисков;
- проще распространять CLI;
- проще подключать к агентским пайплайнам.

Минусы:

- нельзя быстро скопировать готовые исторические методы;
- private API придётся реализовывать clean-room;
- нужно аккуратно документировать источники.

## Review checklist

Перед merge любого private API кода проверить:

```text
[ ] Нет копипаста из GPL-проектов.
[ ] Нет GPL-зависимостей в runtime dependencies.
[ ] Endpoint-и описаны своими словами.
[ ] Реализация покрыта тестами и probe-скриптами.
[ ] THIRD_PARTY_NOTICES.md обновлён.
```

## Revisit criteria

Решение можно пересмотреть только если проект сознательно меняет лицензию или принимает GPL-совместимую модель распространения. Для текущего плана это не требуется.
