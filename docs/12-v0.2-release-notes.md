# 0.2.0 Release Notes — Hermes MailCloud

**0.2.0 introduces the supported command-first Application API.** The CLI remains
JSON-first and rclone-backed. Distribution is a GitHub Release under immutable
`v0.2.0`, not a PyPI publication. Historical 0.1.0 and alpha assets are unchanged
and do not contain this API.

## Application and compatibility

`hermes_mailcloud.application.MailCloudApplication` exposes `version`, `setup`,
`doctor`, `ls`, `stat`, `mkdir`, `upload`, `download`, `mv`, `cp`, `rm`, `publish`,
`link`, `batch(document)` and `batch_file(Path)`. Calls are synchronous and return
a safe typed `ResultEnvelope` without printing or importing Typer/Click/Rich.
CLI handlers translate input and output through that same owner; there is no
legacy execution fallback. Canonical signatures and examples are in the
[current application interface](01-architecture.md#current-in-process-application-interface).

Configuration precedence, overwrite/no-clobber, protected removal, public-root,
confirmation, private-journal and write-once policies remain. No configuration or
journal migration is required. Package version 0.2.0 does not change the batch
JSON version 1 or introduce new envelope/doctor schemas.

Narrow corrections accompanying the shared boundary:

- An omitted CLI profile respects `HMC_PROFILE`, then `default`; an explicit
  `--profile default` still wins. `version` does not read configuration.
- Live doctor without confirmation returns exit 9; confirmed live plus dry-run
  returns invalid arguments/2 before configuration or backend access.
- Batch rejects explicit null defaults and invalid UTF-8, accepts numeric version
  1.0 as JSON version 1, and rejects bool/string/nonfinite versions. Both inputs
  use the real parser and one composition/execution path per batch.
- Unexpected ordinary failures have a fixed safe error without exception content
  or a rollback promise. Partial batch preserves ordered item results, exit 11
  and no top-level error. `BaseException` is not swallowed.

No GUI, MCP/HTTP service, command bus, daemon, background jobs, sync, unlink,
direct-download resolution, link expiry/passwords or full link audit is added.
`yes` expresses process intent, not authentication or new access authority.

## Install and update

Use the exact GitHub wheel, not a registry-name install:

```console
uv tool install --python 3.12 https://github.com/VladimirMonin/hermes-mailcloud/releases/download/v0.2.0/hermes_mailcloud-0.2.0-py3-none-any.whl
hermes-mailcloud --json setup
hermes-mailcloud version
hermes-mailcloud --json doctor
```

For an intentional replacement, add `--force` to that exact installation command.
Retain the existing application profile and separate backend `RCLONE_CONFIG`;
package replacement does not configure credentials or replace a working external
rclone. An operational uv tool has its own interpreter: Python consumers install
the wheel in their own environment. See the [installation guide](11-local-installation.md).

Assets are `hermes_mailcloud-0.2.0-py3-none-any.whl`,
`hermes_mailcloud-0.2.0.tar.gz` and `SHA256SUMS`. Compare downloaded complete-file
SHA-256 values with the manifest before installation. The wheel contains runtime
code/data and license notices, not credentials, tests, rclone or private evidence.
The sdist retains the attributed, unchanged Project Foundation Kit reference.

## Verification boundaries and limits

CI targets Ubuntu/Windows × Python 3.12/3.13, with full disjoint offline packs,
build and clean non-editable installed-wheel checks. Inspect Actions for the
exact release commit; an older green run is not this release's result.
Installed smoke exercises the real launcher separately from fake-backed CLI and
SDK-blocked direct API flows, preserving actual services, parsers, installer,
doctor/probes, journal and native runner. It is not a real Mail.ru test.

Local 0.2.0 qualification uses native Windows x64/Python 3.12 with elevation.
Ordinary-user Windows remains unqualified; this is not an Administrator
requirement or universal platform claim. Default official HTTPS setup evidence
is retained only for unchanged installer behavior, not newly asserted for 0.2.0.
Real-cloud release checks are restricted to a freshly absent owned `/TEST/`
descendant with complete-byte/hash readback and exact cleanup. Production-public
operations and full live doctor are not inferred from that file-operation scope.
A timeout or post-link journal failure can follow an effect: never replay a write
automatically or assume rollback. Existing platform/storage limitations remain in
the [installation](11-local-installation.md#windows-storage-limits) and
[safety](05-safety-model.md) documentation.
