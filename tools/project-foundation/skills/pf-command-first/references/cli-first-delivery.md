# CLI-first: проверить прикладной путь до добавления оболочек

Прочитать целиком, только когда выбран CLI-first маршрут [основного навыка](../SKILL.md).
Это порядок поставки проверяемых срезов, не требование сделать терминал ядром приложения
и не самостоятельное разрешение реализовывать продукт. Для существующего GUI допустим
первый срез через его текущий вход, затем подключение CLI к выделенному сценарию.

## Последовательность и границы готовности

1. **Выбрать один законченный сценарий.** Найти реальный owner и действующий контракт,
   вход, наблюдаемый результат и существенный отказ с сохранностью. Выбрать профиль
   по нужным гарантиям, не создавать будущие очереди/адаптеры заранее. План среза
   не выдаётся за работающий CLI.
2. **Отделить Application API от терминала.** Параметры, правила, результат и ошибки
   доступны без CLI-парсера и GUI. При разрешённой реализации прямой тест проверяет
   настоящий сценарий и результат, а не только вызов mock-метода. Принятая работа
   отличается от готового результата; для B отдельно проверяется получение её итога.
3. **Подключить тонкий CLI.** Использовать найденные entrypoint, help и документацию
   проекта; неизвестные команды/флаги остаются неизвестными. Преобразовать аргументы
   в общий запрос, не перенести в CLI правила имён, хранения, прав или повторов.
   Передавать пути/параметры как данные, не собирать исполняемую строку из ввода.
   Если оборачивается существующий CLI-процесс, его машинный контракт, прогресс,
   остановка и судьба дочернего процесса проверяются отдельно; такая обёртка допустима.
4. **Определить машинный режим.** Устойчивый формат результата — в stdout,
   диагностика — отдельно, обычно stderr; секреты и пользовательское содержимое
   не попадают в вывод по умолчанию. Закрепить смысл кодов завершения, ошибок,
   partial/unknown и ожидания: код успешной отправки не означает успех фоновой работы.
   Неожиданный интерактивный вопрос в автоматизации недопустим: вернуть необходимость
   подтверждения структурированно либо использовать явно выбранный интерактивный режим.
   Не предполагать наличие конкретного флага JSON, ожидания или подтверждения.
5. **Явно выбрать сессию.** Headless не обязан быть stateless. Attached использует
   нужного существующего владельца, а не вторую копию ядра; при его отсутствии — отказ.
   Определить закрытие соединения/CLI, сигналы завершения и судьбу принятой работы.
   Прекращение ожидания и отмену задачи связывать только по явному контракту.
6. **Проверить CLI целиком в разрешённой области.** Synthetic/disposable вход →
   настоящий разбор аргументов → Application API → результат и его readback.
   Для изменяющей операции сверить целевой ресурс и сохранность прежних данных,
   для отказа — его причину и допустимые оставшиеся эффекты. Проверить настоящий
   serialized stdout, диагностический канал и raw exit. При переносе семантики —
   [один канон и соединённый путь](../../../references/methods/contract-evolution.md).
   Help, импорт и корректный JSON не доказывают, что операция доступна и работает.
7. **Добавлять только нужных клиентов.** GUI вызывает API напрямую или через
   выбранный транспорт, не обязан запускать CLI. Он отображает состояние того же
   владельца; при позднем подключении/разрыве восстанавливает его, а не создаёт свою
   очередь. [UI-навык](../../pf-ui-design/SKILL.md) ведёт состояния и визуальную проверку,
   не меняет смысл операций. MCP — ещё один необязательный адаптер с собственными
   протокольными проверками; CLI PASS не доказывает GUI/MCP PASS. Нет требования
   реализовать все интерфейсы или все внутренние функции опубликовать агенту.
8. **Сохранить границу эволюции.** Переход от готового результата к `accepted`/Job,
   общий несохранённый документ, работа без окна и восстановление после сбоя —
   новые обязательства, не бесплатное добавление флага. Согласовать совместимость
   и переход у существующего владельца контракта. Переиспользовать предметную логику,
   где её гарантии сохраняются; не обещать отсутствие будущей переработки.

## Достаточный итог

Сценарий подтверждён через заявленный вход в указанных условиях либо честно остался
NOT_RUN; формат результата/ошибки, режим состояния и границы эффектов известны.
В существующей задаче/проверке указать выбранные команды, наблюдение, raw exits,
подмены и непроверенные режимы. Не создавать второй каталог или обязательный ADR.
Общие evidence/privacy/cleanup правила принадлежат [quality](../../../references/quality.md),
приёмка и обновление затронутых знаний — [lifecycle](../../../references/lifecycle.md).
