# Command-first: операции приложения независимо от оболочек

Прочитать этот файл целиком. Большие источники ниже читать выборочно по задаче.

## Применимость и границы

Для выбора command-first-архитектуры, выделения операций из GUI, CLI-first поставки
или добавления нужного интерфейса к существующему Application API. Вход: сценарий,
текущие owners/контракты, нужные клиенты, гарантии состояния/выполнения и разрешённый scope.
Навык даёт архитектурное решение и проверяемый срез; сопровождение реализации —
только внутри уже разрешённой задачи. Не разрешает переписывание продукта, миграции,
установки, платные вызовы, публикацию или реализацию всех показанных адаптеров.
Для исправления подписи и чисто визуальной задачи этот маршрут не нужен.

Местные правила сохраняют приоритет. Общие owners: [lifecycle](../../references/lifecycle.md),
[metadata](../../references/metadata.md), [quality](../../references/quality.md).
Существенную постановку ведёт [pf-plan](../pf-plan/SKILL.md), визуальное решение —
[pf-ui-design](../pf-ui-design/SKILL.md). Это маршруты, не обязательная цепочка исполнителей.

## Минимально достаточный профиль

Выбирать по наблюдаемым гарантиям, не числу команд, наличию агента или престижу технологии.

| Профиль | Когда необходима эта ответственность |
|---|---|
| **A — прикладной сервис** | Независимая операция возвращает результат. Локальные прогресс и отмена возможны без самостоятельной системы Job. |
| **B — управляемые задачи** | Работа живёт отдельно от запускающего вызова, нужна адресуемая задача и общий контроль её состояния/результата. Хранение в памяти или устойчивое — отдельный выбор. |
| **C — рабочая сессия** | Клиенты изменяют общий живой документ/workspace, включая несохранённое; нужны владелец, согласование и выбранная политика истории/сохранения. |
| **D — устойчивый процесс** | Через сбои и ожидания восстанавливаются зависимые этапы, решения и допустимые переходы, а не только очередь независимых работ. |

A–D — не лестница зрелости. Сочетать только нужное по модулям; сохраняемый B не обязательно D.
Реестр, Job Manager, IPC, подписка, workflow, MCP, CQRS и Event Sourcing не добавляются автоматически.
Размещение, долговечность, полномочия и ресурсные пределы выбирать независимо от буквы профиля.

## Порядок

1. **Найти основу.** Прочитать правила и относящиеся контракты проекта. Назвать реальный
   вход, owner и потребителей; разделить current/proposed. До записи определить конечные
   пути. Неизвестный контракт или право с существенными последствиями — вопрос владельцу,
   не выдуманная сигнатура. Нет нужной дельты — no-op без изменения дат.
2. **Сформулировать обещания.** Записать результат, важный отказ, нецели и сохраняемое;
   что живёт после ответа, закрытия окна/соединения, завершения процесса и перезапуска.
   Выбрать наименее сложное решение, выполняющее эти гарантии, и условие его пересмотра.
3. **Определить независимый Application API.** Команда выражает намерение изменить или
   выполнить, query читает состояние; команда не обязана быть shell-строкой или классом.
   Прикладной сценарий координирует операции и проверки, предметные правила сохраняют
   инварианты, инфраструктура исполняет техническую работу. Ядро не зависит от widgets,
   CLI-парсера или MCP SDK. Для каждого ресурса назвать авторитетного owner-а записи;
   GUI/CLI/MCP получают данные для чтения и запрашивают изменения, не обходят его правила.
4. **Закрепить контракт у одного канона.** Явные цели, вход/defaults, результат, ошибки,
   предусловия, эффекты, права, повтор и отмена по применимости. Отличать принятие,
   завершение, сохранение и частичный результат. Runtime-валидация не заменяет права:
   доверенный контекст устанавливает принимающая сторона, допуск к ресурсу проверяется
   общим прикладным путём. Использовать [имеющуюся форму контракта](../../templates/documents/interface-contract.md.tmpl)
   и [эволюцию контрактов](../../references/methods/contract-evolution.md), без второй схемы/реестра.
5. **Развести режимы и адаптеры.** Headless может иметь собственное состояние без окна;
   Attached обращается к тому же авторитетному владельцу ресурса, что и GUI. Одна библиотека
   или файл на диске этого не обеспечивает. Указать целевую сессию и срок её жизни;
   отсутствие Attached-owner-а — явный отказ, не скрытый запуск другого Headless-ядра.
   Тонкие адаптеры преобразуют ввод/ответ и транспортные ошибки, не дублируют правила.
   CLI может быть первым клиентом; GUI не обязан запускать CLI подпроцессом.
6. **Ограничить эффекты.** Назвать точку применения/публикации, конфликт ресурсов и
   политику частичного исхода. Для опасного действия — согласованный план последствий
   и доверенное подтверждение по политике проекта; перепроверить изменяемые условия
   у точки эффекта. Подготовка/проверка отдельно от публикации там, где нужна сохранность.
   Ошибка после фиксации или потерянный ответ не доказывают отсутствия изменений:
   сначала сверка, повтор только по контракту. Очистка касается только своих учтённых
   данных, не чужих результатов и последующих правок; универсальный exactly-once не обещать.
7. **Добавить управление лишь по требованию.** При длительной работе определить владельца
   итогового состояния, исполнителя и пределы ресурсов. Управляющий запрос не ждёт за
   тяжёлой работой. Прекращение ожидания, запрос отмены, фактическая остановка, Undo,
   компенсация и запрет новых действий сессии различаются. Указать оставшиеся эффекты;
   сильный барьер публикации учитывает уже допущенные действия. При повторах защитить
   и отчёты, и публикацию от старой попытки. GUI читает факты owner-а; опрос либо снимки
   с обновлениями восстанавливают итог после потерь, старое состояние не затирает новое.
   Фокус/прокрутка человека остаются локальными; логи не становятся источником состояния.
8. **Передать срез и критерии.** Для выбранного CLI-first пути читать [приложение](references/cli-first-delivery.md).
   При существующем GUI сначала можно выделить одну его операцию, сохранив поведение.
   Проверки выбирать по обещаниям: прямой путь без GUI, нужный адаптер → реальный owner →
   читаемый результат, существенный отказ/сохранность и только применимые гонки/режимы.
   Прочитанное, спроектированное и реально выполненное различать; недоступный путь — NOT_RUN.
   Если нужен долговечный обзор доступности, использовать [capability-passport](../../templates/documents/capability-passport.md.tmpl),
   не требовать паритета всех интерфейсов. Принятие и завершение — по lifecycle.

Выход: выбранный профиль с причиной/ограничениями, владельцы состояния и эффектов,
ссылка на канон контракта, минимальный следующий срез и фактические проверки/остаток.
Общий API снижает цену адаптеров, но не обещает «никогда не переписывать»:
новые гарантии требуют явной эволюции контрактов, размещения или модели состояния.
