# Bootstrap инженерной документации

## Применимость и вход

Используй при первоначальном внедрении **всего** комплекта или ограниченной повторной сверке. Не используй для массовой миграции архива, замены принятой архитектуры, установки зависимостей приложения или обновления самого универсального пакета.

Вход: явный корень проекта и корень импортированного пакета; потребность/стадия/пользователи; действующие правила и навигация; разрешённые пути/действия; клиент; языки руководств и трекер, если уже выбраны. Название папки не определяет цель продукта.

## Порядок

1. Прочитай native правила проекта до любой записи, затем [жизненный цикл](../../references/lifecycle.md) и [метаданные](../../references/metadata.md). Найди реальные существующие философии, инструкции, сценарии, команды и локальные решения. Различи пустой проект и существующий. Не исследуй private/runtime данные ради подготовки Markdown.
2. Составь короткую таблицу «нужда | существующий механизм | конкретный gap | действие». Для достаточного владельца — использовать существующее. [Форма профиля](../../templates/project-profile.yaml.tmpl) — вариант каталога, не обязательный отдельный YAML. Достаточный существующий owner команд/ограничений можно использовать напрямую; профиль, если нужен, ссылается на канон, не копирует его. Непроверенная команда — не настроена/не проверена, не выдуманный запуск.
3. До записи назови конечный список путей и конфликтов. Не переименовывай местное дерево ради default layout. Не затрагивай чужие изменения. Вопрос о цели/праве/потере данных задай владельцу; второстепенное неизвестное оставь явно draft/предположением без accepted-штампа.
4. Следующие формы — каталог, не квота файлов. Роли основ и инструкций могут быть разделами одного инженерного документа, если им не нужен отдельный жизненный цикл; см. [законченный минимальный пример](../../references/minimal-adoption.md). Создай только недостающее: [философия проекта](../../templates/foundation/project-philosophy.md.tmpl), [архитектурные принципы](../../templates/foundation/architecture-principles.md.tmpl), [тестовая стратегия](../../templates/foundation/testing-strategy.md.tmpl), [наблюдаемость](../../templates/foundation/observability-policy.md.tmpl). Универсальное ядро адаптируй, поля заполни по фактам. Пустой проект получает принципы и намерение, не вымышленную текущую архитектуру.
5. Собери короткий [AGENTS](../../templates/AGENTS.md.tmpl), достаточные [инструкции разработки](../../templates/instructions/development.md.tmpl), [планирования](../../templates/instructions/planning.md.tmpl), [Git](../../templates/instructions/git.md.tmpl), [документации](../../templates/instructions/documentation.md.tmpl), [создания инструкций](../../templates/instructions/instruction-authoring.md.tmpl), [тестирования](../../templates/instructions/testing.md.tmpl), [логирования](../../templates/instructions/logging.md.tmpl) и [руководств](../../templates/instructions/guides.md.tmpl). Уже достаточные документы остаются owners; новые ненужные файлы не создавай. Вход — [docs-index](../../templates/documents/docs-index.md.tmpl), не библиотека в root.
6. Добавь необходимые двусторонние маршруты. Для программируемых операций или будущей второй оболочки предложи [pf-command-first](../pf-command-first/SKILL.md), не навязывая его каждому скрипту и не загружая всю библиотеку. Только при реальной UI-потребности предложи [pf-ui-design](../pf-ui-design/SKILL.md); CLI без GUI не получает UI-документы. Объясни, что `{{field_name}}` заполняет агент, не встроенный Templates. При запросе Obsidian используй [поставляемые views](../../templates/obsidian/README.md) над теми же файлами, без второй вики. Опциональные папки/формы не создавай пустыми.
7. Выбери подключение по фактическому клиенту: [Pi](../../integrations/pi.md), [Hermes](../../integrations/hermes.md), [явное чтение](../../integrations/generic.md). Не менять глобальную среду и не обещать auto-load по одному наличию AGENTS. Отдельно проверить обнаружение, выбранный путь навыка, чтение его ресурсов и отсутствие коллизий.
8. Проверь заполнение/типы/ID/локальные ссылки, полезность routes и соответствие имеющимся знаниям; команды только по [проверочному owner-у](../../references/quality.md) в разрешённых пределах. Передай результат по [местной политике приёмки](../../references/lifecycle.md#владелец-приёмки-и-повторных-проверок); не назначай нового reviewer-а поверх неё и не называй авторскую проверку независимой.

## Повтор и обновление

При повторном применении читай текущую адаптацию и предыдущую версию пакета, если отмечена. Достаточно и нет дельты — no-op, не трогай даты. Нужна дельта — изменяй существующий owner адресно, сохрани ручные дополнения. Противоречие показывай точно: файл/действующее правило/предлагаемая дельта/влияние; шаблон не победитель по умолчанию. Обновление ресурсов пакета и изменение местных документов — разные операции, не автоматическое слияние.

## Результат и остановка

Достаточная связная основа с реальными путями/честно неизвестными командами, коротким профилем или ссылкой на его канон, работающей навигацией и конечным остатком. Сообщи изменённые пути, проверки/ограничения, что сохранено и кем, какие решения отсутствуют. После этого остановись, не создавай архитектурную программу или обязательную цепочку из семи агентов.

**Правильно (учебно):** у небольшой CLI-утилиты нет docs; подтверждён один вход. Создать краткие принципы/инструкции, записать тестовую команду как непроверенную до разрешённого запуска, не рисовать будущий API как реализованный.

**Неправильно:** заменить существующий AGENTS шаблоном, скопировать один SKILL без общих ресурсов, придумать `npm test` и объявить проект развёрнутым/проверенным.
