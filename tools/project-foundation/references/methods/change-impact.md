# Влияние изменения до и после работы

## Триггер и граница

Общий формат, несколько consumers, сохраняемые данные или существенный риск.
Малой локальной правке достаточно одного предложения. Метод уточняет выбор checks,
не требует полного repo-audit, scanner-а, графовой БД или нового impact ledger.

## До изменения

1. Установить фактический root, исходную редакцию/базу, разрешённые пути и dirty
   intersections. При indexed lookup подтвердить root/freshness/selection; no-match
   не доказывает отсутствие consumers. Обычный source tracing достаточен.
2. Найти изменяемого owner-а и непосредственных значимых consumers по свидетельствам:
   import/call, маршрут, serializer/reader, конфигурационный selector, generator.
   Назвать неизвестную связь неизвестной, не превращать предположение в факт.
3. В существующей задаче записать коротко «граница → подтверждение связи → риск →
   достаточная проверка». Например, serializer → вызов reader-а → null станет нулём →
   реальные bytes и consumer assertion. Не добавлять CLI/GUI, которых у проекта нет.
4. Выбрать согласованный scope и проверки по поведению/цене отказа. Достижимость
   модуля не означает обязательный самый дорогой E2E. Неясная дорогая граница требует
   адресной проверки или решения owner-а, не удобного no-impact.

## После изменения

5. Сопоставить ожидаемое влияние с **настоящей дельтой**, включая поля, ошибки,
   миграции, генерацию, команды/конфигурацию и знания. В Git выбрать базу по задаче:
   branch comparison с согласованным ref/base, а не только пустой `git diff`.
   Учесть относящиеся committed, staged, unstaged и untracked paths. Для ориентира:
   `git diff <base> HEAD`, `git diff --cached`, `git diff`, `git status --short`.
   Это примеры просмотра, не универсальная политика выбора merge-base. Clean tree
   не значит «в ветке ничего не изменилось». Чужая dirty работа остаётся чужой.
6. Проверить значимых consumers изменившегося контракта. Для сериализации применять
   [contract-evolution](contract-evolution.md), для конкретного бага —
   [behavior-regression](behavior-regression.md). Не повторять неизменённое evidence
   без нового основания; назвать его применимость к артефакту/fixture/окружению.
7. Если actual scope вышел за разрешение, передать дельту owner-у задачи. Правка
   плана задним числом не легализует новые права. Устойчивое знание обновить у его
   существующего owner-а; out-of-scope consumer — точный handoff, не скрытая запись.
8. Читать результаты, selection, skips/warnings и ограничения, не один exit.
   Downstream failure требует причины/связи; «это baseline» — свидетельства той же
   причины на подходящей базе, не одинакового числа failures.

## Выход и остановка

В задаче остаются actual scope/base, подтверждённые связи, достаточные команды/сырые
exits, объяснённые исключения и конкретный остаток. Нет обязательного REGRESSION.md,
квоты TEST-ID или нового backlog. Остановиться после проверки изменённой границы,
не обследовать всю историю ради метода. Приёмка и переиспользование —
[lifecycle](../lifecycle.md), границы доказательства — [quality](../quality.md).
Происхождение — [UPSTREAM](../../UPSTREAM.md).
