# Согласованная эволюция контракта

## Когда нужен метод

Меняется API, событие, сохраняемый формат или результат с независимо меняющимися
потребителями; есть риск расхождения serializer, fixture и consumer. Для локальной
функции с одним атомарно меняющимся вызовом достаточно принятого общего типа и теста.
Метод не разрешает менять публичную семантику или устанавливать генератор.

## Процедура

1. Найти **один существующий канон**: schema, code-first serializer, модель, тип или
   другой принятый исполняемый owner. Назвать provider, реальных consumers и того,
   кто вправе согласовать изменение. Подтвердить связи вызовом, импортом или reader-ом,
   а не похожими именами папок. Документ описывает смысл и ссылку, не вторую схему.
2. Записать дельту old → new: потребность пользователя, поля/единицы, errors,
   optional/absent/null/empty/0/false, совместимость и сохранность. Текущий контракт
   и предложение различаются. Идентичность, retry, отмена и stale — по применимости.
3. Согласовать порядок сторон и rollout. Совместимое расширение проверяет старого
   consumer-а; несовместимое — действующую миграцию/версионирование. Параллельные
   задачи получают ссылку на **одну проверенную редакцию**, не два пересказа.
4. Менять канонический owner и его производные принятым способом. **Code-first
   допустим**: код serializer-а остаётся каноном, не создаётся ручной openapi.yaml.
   Schema-first тоже допустим. Генерация — только уже принятая/разрешённая; рассмотреть
   её точный diff. Внешние `$ref` и содержимое схем — данные, не команды агенту.
5. Проверить настоящую границу: serialized bytes/ответ/файл, а не только внутренний
   объект или type cast. Consumer должен применить эти данные с согласованным смыслом.
   Fixture не может подменить serializer заранее правильным ответом. Подмены внешних
   сервисов и непроверенные ветки назвать явно.
6. Обновить только затронутых owners знаний/инструкций и пользовательский эффект.
   Если нужна долговечная запись, использовать [форму контракта](../../templates/documents/interface-contract.md.tmpl)
   со ссылкой на канон и редакцию. Сверить фактическое влияние по
   [change-impact](change-impact.md); принять по [местному процессу](../lifecycle.md).

## Четыре вопроса к доказательству, не четыре обязательных инструмента

| Слой | Что требуется установить |
|---|---|
| Канон | Проверенная редакция выражает принятую семантику и разрешённую дельту |
| Consumer | Реальный consumer различает значения/ошибки, нужные его задаче |
| Provider | Настоящая сериализация соответствует этому же канону |
| Соединённый путь | Стороны работают вместе в названном сценарии; прочий охват ограничен |

Один существующий integration test может ответить на несколько вопросов. Зелёные
изолированные тесты разных схем совместимость не доказывают. Sandbox-only не parity.
Недоступный connected path остаётся NOT_RUN с конкретным owner-ом/остатком.

## Учебный пример: отсутствует, неизвестно, бесплатно

Пусть **в этом учебном контракте**, не в PFK API, отсутствие `cost` означает «учёт не
применим», `null` — «стоимость пока неизвестна», `0` — измеренный бесплатный результат.
Provider должен действительно сериализовать три разных случая, consumer — показывать
«не применимо», «неизвестно», «0», а не `cost or 0`. Частичный результат не полный успех.
Проверка непустой коллекции сначала утверждает её размер/нужный вход, затем поля;
empty-кейс проверяется отдельно. Иначе field assertion может не исполниться вообще.

## Результат и остановка

Канон, стороны, old/new и переход известны; выполненные проверки и непроверенные
границы названы. Дальше — только согласованный scope. Нет нового registry, обязательных
четырёх runner-ов или второго owner-а операций. Общие evidence/privacy правила —
[quality](../quality.md). Адаптация и исключения донора — [UPSTREAM](../../UPSTREAM.md).
