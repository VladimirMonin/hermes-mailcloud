# Содержательная поведенческая регрессия

## Когда применять

Есть конкретный дефект или риск неверного наблюдаемого результата. Метод помогает
выбрать проверку; право исправлять код остаётся у автора по местной инструкции.
Это не требование TDD для каждой правки, 80% покрытия или checkpoint-коммитов.

## Короткий путь

1. Найти принятое требование/контракт/сценарий. Сформулировать ожидаемый результат,
   существенный неправильный исход и инвариант. Текущая реализация не oracle сама
   для себя. Для опечатки достаточно текстовой проверки, не unit-ритуала.
2. Подобрать безопасный минимальный input. Найти реальный runner/selection и путь
   от входа к subject/consumer. До collection учесть side effects и disposable
   roots по [quality](../quality.md). Не выдумывать pytest/npm test.
3. Запустить выбранный случай. Установить, что он **достиг нужного пути** и упал
   именно по предметному неверному результату. Collection/import/dependency failure,
   синтаксическая ошибка или неправильная fixture — не RED продукта. Сохранить
   исходный failure, исправить разрешённую причину fixture и повторить путь.
4. Внести минимальную разрешённую коррекцию у настоящего owner-а. Не менять oracle,
   ослаблять assertion или подменять subject ради GREEN. Отдельный refactor необязателен.
5. Повторить **тот же тест/вход/существенные условия** и прочитать наблюдение GREEN.
   Какой конкретный неверный результат он отвергает? При необходимости проверить
   отрицательный контроль в собственной безопасной копии, не портить чужую ветку.
6. Проверить affected consumers по [change-impact](change-impact.md), обновить только
   устойчивую дельту знаний и передать результат по [местной политике](../lifecycle.md).

Для новой функции ещё нет исторического бага: нужны позитивный/негативный критерии,
а не выдуманное старое RED. Для невоспроизводимого отказа назвать основание гипотезы,
доступную проверку и точный остаток. Визуальная композиция требует rendered evidence,
не удачного import. Отсутствие запуска остаётся NOT_RUN, не PASS и не N/A.

## Проверка, которая не может молча пропустить свой предмет

| Риск слабого теста | Содержательная замена |
|---|---|
| `if items: assert field` при пустом результате | Для field-кейса обеспечить непустую fixture, assert количества и полей; empty проверить отдельно |
| Только sandbox назван parity | Исполнить обе реальные доступные ветки против одного контракта либо ограничить вывод sandbox и назвать непроверенную ветку |
| Только HTTP 200 / файл существует | Проверить значения/байты/readback и нужный consumer |
| Fake сам возвращает ожидаемый результат subject-а | Подменить только внешний край, оставив предметную логику/применение настоящими |
| Проверка только call count | Проверить результат и сохранность, включая значимый отказ |

Пример отрицательного контроля: непустой ответ из двух объектов без обязательного
поля должен отвергаться field-тестом. Пустая коллекция не может служить доказательством
наличия поля; отдельный empty-кейс проверяет согласованное пустое поведение. Для
parity нужны две реально исполненные ветки, не два имени одной fixture.

## Свидетельство и остановка

Достаточно связи «требование → test/node → команда/selection → raw RED/причина →
та же GREEN → затронутые consumers/limits» в задаче или существующей
[verification-форме](../../templates/documents/verification.md.tmpl). Не нужен новый
реестр тестов, evaluator или аттестация проверяющего. Raw exit сам по себе не verdict.
После согласованного результата остановиться; нет новой информации — нет нового
обязательного цикла. Адаптированные источники — [UPSTREAM](../../UPSTREAM.md).
